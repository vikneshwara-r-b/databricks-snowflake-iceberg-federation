# Terraform — Snowflake reads Unity Catalog tables

One Terraform project, one state. Provisions the AWS/Databricks/Snowflake plumbing for
Snowflake to read this project's Unity Catalog tables directly — originally just the 3
gold/analytics tables, now nearly every table across all three schemas (`raw`,
`curated`, `analytics`; see `src/utility/snowflake_sync_config.json` for the full
source→target mapping — `race_raw_quarantined` is the one deliberate exclusion,
quarantined/rejected records aren't meant to be externally readable) — via UniForm +
the Iceberg REST Catalog API + credential vending. See the
[Databricks blog post](https://www.databricks.com/blog/read-unity-catalog-tables-in-snowflake)
this implements.

The actual Snowflake DDL runs from two notebooks, not from Terraform (which only
provisions the identity/access/storage plumbing around them):
- `src/utility/create_snowflake_catalog_integration.ipynb` — `CREATE CATALOG
  INTEGRATION`, run **manually, once**, per environment/catalog. Not wired into any
  job, since the integration only needs to exist once.
- `src/utility/sync_to_snowflake.ipynb` — `CREATE`/`ALTER ICEBERG TABLE`
  against that integration. Run as three separate tasks on the
  `f1_ingest_and_transform_workflow` job — `{raw,curated,analytics}_snowflake_share`
  — one per layer, right after that layer's own pipeline, each
  passing a different `layer` widget value to scope which part of
  `snowflake_sync_config.json` it processes, and a `pipeline_id` widget — the DAB
  bundle passes it directly from `resources.pipelines.*.id`, no runtime job/task
  introspection needed. Before refreshing an already-existing table, one
  `event_log(pipeline_id)` call per layer (`GROUP BY flow_name`, not one
  `event_log()` call per table) checks whether its latest pipeline update actually
  changed anything, skipping the `REFRESH` call if not — no custom state table
  involved. Streaming tables and materialized views need different signals for
  this: an MV's `num_output_rows` is always its full recomputed row count, not an
  incremental delta, so it's checked via the `planning_information` event's chosen
  maintenance technique instead (`MAINTENANCE_TYPE_NO_OP` means nothing changed).

## What this project creates

- `aws_storage.tf` — S3 bucket + IAM role/policy for the Unity Catalog storage
  credential. Also resolves a real bootstrap problem: the role's trust policy needs
  an `external_id` that only exists once Databricks generates it for the storage
  credential (`databricks_catalog.tf`) — a response-only field, confirmed against the
  Create Storage Credential REST API docs, not something a client can set. The role
  is created with a placeholder trust policy, then `null_resource.fix_trust_policy`
  shells out to `aws iam update-assume-role-policy` (via a `local-exec` provisioner)
  to patch in the real one once it's known — all within a single `terraform apply`,
  no manual step or second apply needed. **Requires the AWS CLI (`aws`) installed and
  on `PATH`**, in addition to it being configured with `var.aws_profile`.
- `secrets.tf` — one Secrets Manager secret holding every Snowflake credential,
  namespaced under `admin`/`service_user` keys: the admin identity's credentials
  (from sensitive `terraform.tfvars` values) and the Snowflake service user's
  credentials (generated by Terraform itself — see `snowflake.tf`).
- `kms.tf` — a customer-managed KMS key encrypting that secret.
- `databricks_catalog.tf` — storage credential → external location → the `f1_analytics`
  catalog itself (replaces the old manual `CREATE CATALOG IF NOT EXISTS` notebook step
  for `prod`).
- `databricks_access.tf` — a Databricks service principal (OAuth M2M) with the
  `workspace_access` entitlement (service principals get none by default — without
  it, every workspace API call is rejected with a 403 regardless of any catalog/
  schema grants) + the Unity Catalog grants it needs for credential vending. This
  same service principal is reused — not a separate identity — as the `run_as`
  identity for the `f1_ingest_and_transform_workflow` job (`databricks.yml`, `prod`
  target), so its catalog grants also include `MODIFY`/`CREATE TABLE`/
  `CREATE MATERIALIZED VIEW`/`READ VOLUME`/`WRITE VOLUME`, and it has `READ` on the
  Snowflake secret scope. `CREATE MATERIALIZED VIEW` is a separate Unity Catalog
  privilege from `CREATE TABLE` — needed specifically for the gold layer's
  materialized views; `CREATE TABLE` alone covers raw/curated's streaming tables but
  isn't sufficient for the analytics pipeline. `databricks.yml`
  resolves its `application_id` itself, at deploy time, via a bundle variable
  `lookup` on its `display_name` — nothing to copy from Terraform manually. The
  `job_runner_application_id` output exists only as a convenience for manual
  inspection/debugging. Also grants whoever `var.databricks_profile` authenticates
  as the **"Service principal: User"** role on this SP
  (`databricks_access_control_rule_set.snowflake_reader_user`) — required by
  Databricks before that identity can set this SP as a job/pipeline's `run_as`; see
  Prerequisites item 4 below for why this needs its own grant.

  **`terraform apply` succeeding does not mean `display_name` is actually visible
  yet — verified against the provider's own source, not just observed behavior.**
  `scim/resource_service_principal.go` in
  `github.com/databricks/terraform-provider-databricks` implements Update as a
  single `PUT /preview/scim/v2/ServicePrincipals/{id}` with no follow-up `GET` to
  confirm the new value stuck, no retry, and no consistency-wait logic of any
  kind — a `2xx` response from that one `PUT` is the entire basis for "Modifications
  complete." Separately, Databricks' own Terraform docs state that on an
  identity-federated workspace, workspace-level *creation* of a service principal
  "automatically synchronizes the service principal to the related Databricks
  account" — but say nothing about whether a later attribute *update* propagates to
  the account-level canonical record (which `databricks service-principals get`
  reads back, on this workspace) on the same timeline, asynchronously, or at all
  without something else triggering it. Put together: a rename was checked live
  immediately after a successful apply and still showed the old name; checking again
  later (after unrelated troubleshooting, including the `api = "account"` incident
  below) showed the new name. Whether that was the original `PUT` finally
  propagating on its own, or a manual account-console rename made around the same
  time, can't be distinguished after the fact — both are consistent with what the
  provider's own code does (or rather, doesn't do: confirm the write). Practical
  takeaway: don't trust `terraform apply`'s success message alone for this
  attribute on this resource type if it matters that the change is visible
  immediately — confirm with `databricks service-principals get` or a subsequent
  `terraform plan` instead.

  **Do not set `api = "account"` on this resource.** It fails outright with `Not
  Found` for this workspace's SP (workspace-local numeric IDs aren't valid
  account-level lookups), and — discovered the hard way — Terraform persists `api =
  "account"` into state as part of planning the update *before* the call errors.
  Every subsequent refresh then queries the account-level API for a workspace-local
  ID, gets nothing back, and concludes the resource was deleted — which would cascade
  into recreating this SP and everything keyed to its `application_id` (the secret,
  `databricks_access_control_rule_set.snowflake_reader_user`, the catalog/external-
  location grants, the Databricks secrets) on the next real `apply`, minting a new
  `application_id` and silently breaking all of it. If this ever happens again:
  `terraform state rm databricks_service_principal.snowflake_reader` followed by
  `terraform import databricks_service_principal.snowflake_reader <numeric-id>`
  restores an accurate state (both operations only touch Terraform's local
  bookkeeping, never real infrastructure) — confirm with `terraform plan` showing
  "No changes" before trusting it again.
- `snowflake_data.tf` — the warehouse, database, and schema(s) the service user reads
  and writes Iceberg table data in, created under the **SYSADMIN** role. One schema
  per Databricks schema being synced (`var.snowflake_sync_schemas`, default
  `["ANALYTICS", "RAW", "CURATED"]`).
- `snowflake.tf` — generates an RSA key pair, creates the Snowflake service user with
  it (`snowflake_service_user`), and creates/grants the role that user needs
  (including read/write on the database/schema from `snowflake_data.tf`).
- `databricks_secrets.tf` — a Databricks secret scope holding every credential the sync
  notebook needs, so nothing sensitive is ever typed into notebook code or job
  parameters.

## Auth model

- **AWS** / **Databricks**: named CLI profiles (`var.aws_profile`,
  `var.databricks_profile`), never the ambient default credential chain.
- **Snowflake**: Terraform's own `snowflake` provider (`providers.tf`) authenticates
  via **key-pair (JWT)** auth off the `snowflake_admin_*` variables — never
  username/password, and never by reading back the secret those same variables get
  written into. That distinction matters: a Terraform provider can't be configured
  from a resource created in the same apply (that's a real circular dependency), but it
  can be configured from a plain input variable with no issue, even if that same
  variable is also used elsewhere to populate a resource. There's no cycle, so this
  stays a single project/apply.
- The admin identity is a **dedicated service user** (`SVC_IAC_ADMIN`, or whatever you
  name it — generic, not tied to "Terraform" specifically, so it isn't implicitly
  retired if the tooling ever changes), not a human's personal account. It's created
  once, manually, by a human `ACCOUNTADMIN` (since Terraform can't bootstrap the very
  credential it needs to authenticate itself), then used by every `terraform apply`
  after that — the human's own key never goes in `terraform.tfvars`. It only needs
  `SECURITYADMIN` + `SYSADMIN` granted, not `ACCOUNTADMIN` itself (see Prerequisites).
- The **service user** the sync notebook connects as is fully Terraform-managed:
  `snowflake.tf` generates its RSA key pair (`tls_private_key`) and creates it
  (`snowflake_service_user`) — no manual key generation or `CREATE USER` needed.
- Every Snowflake credential — org/account identifiers, the admin identity's private
  key (supplied via `terraform.tfvars`, never committed), and the generated service
  user's private key — ends up in AWS Secrets Manager via `secrets.tf`.

## Prerequisites (one-time, manual)

1. A metastore admin must enable Unity Catalog's `external_access_enabled` setting on
   the workspace's metastore (Public Preview). On the metastore backing this project's
   `f1_analytics` catalog it was confirmed live to be `false`, which was the actual
   cause of Snowflake's "Failed to retrieve credentials from the Catalog …
   Please ensure that the catalog vends credentials" error (Snowflake error 004174).
   It has since been enabled — see "Confirmed working" below — so this step is already
   done for this project's workspace, and remains a prerequisite for any new one.
   This is a **metastore-wide** toggle — layered underneath and separate from every
   catalog-level `EXTERNAL USE SCHEMA`/`EXTERNAL USE LOCATION` grant this project's
   Terraform already manages; those grants are necessary but not sufficient without
   this. It is deliberately **not** managed by this project's Terraform: the metastore
   is a shared, pre-existing resource, owned outside this project, spanning
   every catalog in the workspace, not just this project's — one project's
   `terraform apply` shouldn't flip a setting with that blast radius. Run once, out of
   band, by whoever holds metastore-admin rights.

   First, get the metastore id for your workspace (it differs per workspace, so read
   it rather than copying one from elsewhere):
   ```bash
   databricks metastores current --profile <your-databricks-cli-profile>
   ```
   This returns the `metastore_id` your workspace is assigned to (no metastore-admin
   privilege needed, just workspace access). Then enable external access on it:
   ```bash
   databricks metastores update <metastore-id> \
     --external-access-enabled=true --profile <your-databricks-cli-profile>
   ```
   Verify it took effect with:
   ```bash
   databricks metastores summary --profile <your-databricks-cli-profile>
   ```
   (`metastores summary` also returns the `metastore_id`, plus every other field —
   `external_access_enabled`, `owner`, `delta_sharing_scope`, etc. — in one call, so
   either command works for the lookup; `current` is the narrower, workspace-scoped
   one.)

   **Confirmed working:** running the `databricks metastores update` command above is
   what actually fixed the Snowflake credential-vending error —
   `external_access_enabled` flipped to `true` and the sync notebook's `CREATE
   ICEBERG TABLE`/`ALTER ICEBERG TABLE ... REFRESH` calls then succeeded.

   **Why it's not in the Databricks Account Console:** this isn't an account-level
   setting at all, so it was never going to be there. Databricks surfaces it as a
   *workspace* setting instead — Catalog Explorer → gear/settings icon →
   **Metastore** → **Details** tab → **External data access** toggle, from any
   workspace attached to the metastore. That control is, per Databricks' own docs,
   "only displayed for sufficiently privileged users" — so even in the right place,
   an under-privileged user sees nothing. It defaults to off specifically "to prevent
   unauthorized external access," a deliberate security default, not an oversight.
   The CLI/API path above remains what this project relies on regardless, since it's
   scriptable and doesn't depend on finding the right screen.

   **Could Terraform manage this instead?** The `databricks_metastore` resource does
   expose `external_access_enabled` as a real argument, and supports `terraform
   import` for an already-existing metastore — so technically, yes. Deliberately
   **not done here**: this metastore is shared/multi-tenant (other workspaces and
   catalogs depend on it, and it is owned outside this project), and importing it
   into this project's state would (a) make the entire shared metastore a destroy
   candidate in this project's state — a stray `terraform
   destroy`, even one aimed at an unrelated resource, would now have a path to it —
   (b) require metastore-admin-level credentials more privileged than anything else
   `terraform/providers.tf` needs today, and (c) risk a destroy/recreate of the
   shared metastore if config and live state ever drift on one of its `ForceNew`
   attributes (e.g. `storage_root`). Same reasoning already applied to keeping the
   Snowflake catalog-integration bootstrap manual instead of Terraform-managed — a
   one-time or shared-scope action shouldn't be owned by a single project's apply/
   destroy blast radius.

   **Correction:** an earlier pass checked this against the CLI's *default* profile,
   which turned out to point at an entirely unrelated workspace/account (no
   `f1_analytics` catalog exists there at all) — it happened to also show
   `external_access_enabled: false`, but that was a different metastore and the
   finding didn't apply to this project. Always pass the explicit Databricks CLI
   profile for this project's actual workspace (`databricks auth describe --profile
   <name>` should show a host whose catalog list includes `f1_analytics`) — never rely
   on whatever profile happens to be the ambient default.
2. A named AWS CLI profile and a named Databricks CLI profile, both pointed at the
   right account/workspace (`databricks auth login --host <workspace-url> --profile
   <name>`).
3. A dedicated Snowflake service user for the **admin identity** Terraform
   authenticates as — this bootstrap step genuinely can't be automated, since it's the
   credential Terraform uses to create everything else, including the sync notebook's
   service user. Create it once, as a human `ACCOUNTADMIN`:
   ```bash
   openssl genrsa 2048 | openssl pkcs8 -topk8 -inform PEM -out admin_rsa_key.p8 -nocrypt
   openssl rsa -in admin_rsa_key.p8 -pubout -out admin_rsa_key.pub
   grep -v -e '^-----' admin_rsa_key.pub | tr -d '\n'   # paste this into the CREATE USER below
   ```
   ```sql
   -- as a human ACCOUNTADMIN, one time only
   CREATE USER SVC_IAC_ADMIN
     TYPE = SERVICE
     RSA_PUBLIC_KEY = '<public key body from above>'
     COMMENT = 'Dedicated infrastructure-automation identity';

   GRANT ROLE SECURITYADMIN TO USER SVC_IAC_ADMIN;
   GRANT ROLE SYSADMIN TO USER SVC_IAC_ADMIN;

   -- SECURITYADMIN's MANAGE GRANTS does not extend to account-level privileges like
   -- CREATE INTEGRATION — Snowflake restricts granting those specifically to
   -- ACCOUNTADMIN or a role that already holds the privilege WITH GRANT OPTION. This
   -- one-time grant lets SECURITYADMIN (and so SVC_IAC_ADMIN) grant CREATE INTEGRATION
   -- to the service role in snowflake.tf without needing full ACCOUNTADMIN itself.
   GRANT CREATE INTEGRATION ON ACCOUNT TO ROLE SECURITYADMIN WITH GRANT OPTION;
   ```
   `SVC_IAC_ADMIN` only needs these two roles, not `ACCOUNTADMIN` — `SECURITYADMIN`
   covers everything the primary `snowflake` provider does (`CREATE USER`,
   `CREATE ROLE`, `MANAGE GRANTS`), and `SYSADMIN` is what the `snowflake.sysadmin`
   provider alias (`providers.tf`) activates for `snowflake_data.tf`'s
   warehouse/database/schema. The explicit `GRANT ROLE SYSADMIN` is required here
   because, unlike `ACCOUNTADMIN`, a plain `SECURITYADMIN`-only user can't activate
   `SYSADMIN` without it.

   Put `SVC_IAC_ADMIN` and `admin_rsa_key.p8`'s contents into `terraform.tfvars` as
   `snowflake_admin_user` / `snowflake_admin_private_key_pem` (`snowflake_admin_role`
   stays `SECURITYADMIN`, the default in `variables.tf`), then securely delete
   `admin_rsa_key.p8`/`.pub` from disk.
4. Whoever runs `databricks bundle deploy -t prod` needs the **"Service principal:
   User"** role on `svc-f1-analytics-automation` — without it, deploy fails with
   `403 PERMISSION_DENIED: Cannot bind the service principal provided in 'run_as'
   field ... The user creating or updating the pipeline must have
   'servicePrincipal.user' role on the service principal.` This is **not** implied by
   being a workspace admin, nor by being the user who created the SP in the first
   place (Databricks' "Service principal: Manager" role, which creators/admins do
   get, deliberately does not include "Service principal: User" — they're separate
   grants).

   **This is now Terraform-managed** —
   `databricks_access_control_rule_set.snowflake_reader_user` (`databricks_access.tf`)
   grants it to whichever identity `var.databricks_profile` authenticates as. One
   CLI/Terraform wrinkle worth knowing: a raw CLI probe (`databricks account
   access-control get-rule-set`/`get-assignable-roles-for-resource`) against this
   exact rule set returned `Not Found` from a workspace-scoped profile — but the
   Terraform provider (same profile) reaches the same API successfully via its
   workspace-level routing, confirmed via `terraform import` before the first apply.
   Also confirmed live: this resource is **authoritative** — applying it replaces
   every `grant_rule` on the rule set, not just adds one — and the rule set already
   had `roles/servicePrincipal.manager` auto-granted to the SP's creator, so that
   role is listed in the config alongside `roles/servicePrincipal.user` to avoid
   silently revoking it. If this is ever extended to a different/additional
   principal, check current live grants first (`terraform import` or `terraform
   state show databricks_access_control_rule_set.snowflake_reader_user`) rather than
   assuming `grant_rules` starts empty.

   Requires `var.databricks_account_id` (not the workspace id —
   `databricks auth describe --profile <profile>` prints it) in `terraform.tfvars`.

   If this ever needs doing manually instead (e.g. for a different deploying
   identity Terraform doesn't also manage):
   1. In the Databricks workspace: **Settings → Identity and access**
   2. Next to **Service principals**, click **Manage**
   3. Select **`svc-f1-analytics-automation`**
   4. **Permissions** tab → **Grant access**
   5. Add the deploying user/group, role **"Service principal: User"**
5. Being able to set `run_as` (item 4 above) is necessary but not sufficient —
   `run_as` only changes which identity *executes* the job/pipelines; it doesn't
   grant that identity access to the workspace files (notebooks) `databricks bundle
   deploy` writes, which stay owned by whoever ran that command. Without the fix
   below, the job fails at run time with: `Unable to access the notebook
   "/Workspace/PROD/.bundle/f1_analytics/prod/files/..." in the workspace. Either it
   does not exist, or the identity used to run this job,
   svc-f1-analytics-automation, lacks the required permissions.` This is handled
   in `databricks.yml` itself, not Terraform — a top-level `permissions:` block
   under the `prod` target grants the SP `CAN_MANAGE`, which (per Databricks' own
   docs on bundle permissions precedence) cascades to "resources, workspace
   directories, and files specified in the bundle," not just job/pipeline resource
   ACLs. The deploying identity is also explicitly included (as the `admins` group,
   not a named person) — `databricks bundle validate` otherwise emits a
   recommendation warning that `CAN_MANAGE` would only apply while the same identity
   keeps deploying.

## The Snowflake warehouse, database, schema, service user, and role (fully automated)

`snowflake_data.tf` and `snowflake.tf` handle all of this on `terraform apply` —
nothing manual:

- `snowflake_warehouse.service_user`, `snowflake_database.uc_sync`,
  `snowflake_schema.sync` (`snowflake_data.tf`, one per `var.snowflake_sync_schemas`
  entry) — created via the `snowflake.sysadmin`
  provider alias in `providers.tf`, so they're owned by **SYSADMIN**, matching
  Snowflake's standard convention (SYSADMIN owns compute/storage objects;
  SECURITYADMIN/ACCOUNTADMIN own users/roles/grants). These resource types have no
  separate "owner" argument — whichever role's session creates the object owns it,
  which is exactly why the aliased provider is the mechanism here, not a
  grant-ownership transfer afterward.
- `tls_private_key.service_user` generates a 2048-bit RSA key pair.
- `snowflake_service_user.service_user` creates the user with that public key (this
  resource type is always `TYPE = SERVICE` — password auth isn't possible for it at
  all), with the warehouse above as its default.
- `snowflake_account_role.uc_iceberg_reader` + `snowflake_grant_privileges_to_account_role`
  create the `UC_ICEBERG_READER` role (name configurable via `var.snowflake_role_name`)
  and grant it:
  - `CREATE INTEGRATION` (account-level) — to run `CREATE CATALOG INTEGRATION`.
  - `USAGE` on the warehouse — to run DDL/queries at all.
  - `USAGE` on the database, `USAGE` + `CREATE ICEBERG TABLE` on the schema — to create
    the Iceberg table objects.
  - `SELECT`/`INSERT`/`UPDATE`/`DELETE`/`TRUNCATE` on all current *and future* tables
    in the schema — actual read/write access to the table data itself, not just the
    ability to create the table objects.
  - `snowflake_grant_account_role.to_service_user` attaches the role to the user.

  *(Public Preview feature — confirm this privilege set against current Snowflake docs
  before relying on it; `terraform validate` confirms the HCL is structurally correct,
  but can't confirm these specific privilege strings are what Snowflake's Iceberg REST
  catalog integration actually requires. Separately: tables synced via vended
  credentials are normally a read-mostly mirror of Databricks-owned data — the
  INSERT/UPDATE/DELETE/TRUNCATE grants exist because they were asked for, but
  Snowflake/Databricks may reject actual writes against a vended-credential Iceberg
  table regardless of the grant. Confirm if write-back is genuinely needed.)*

This relies on `var.snowflake_admin_user` being able to activate `SYSADMIN` — covered
by the explicit `GRANT ROLE SYSADMIN TO USER SVC_IAC_ADMIN` in Prerequisites step 3
above, since a plain `SECURITYADMIN` grant alone doesn't include it.

The generated private key is written into Secrets Manager (`secrets.tf`) and the
Databricks secret scope (`databricks_secrets.tf`) in the same apply — it's never
printed, output, or typed anywhere by hand. One trade-off worth knowing: it *does* land
in `terraform.tfstate` in plaintext (every resource attribute does — `sensitive` only
hides values from CLI output, not from state). That's the same category of exposure
this project already accepts for the admin credentials passed via `terraform.tfvars`;
treat `terraform.tfstate` with the same care as a secrets file — encrypt the backend,
restrict who can read it.

## Apply

```bash
cd terraform
cp terraform.tfvars.example terraform.tfvars   # fill in — this file holds raw key material
terraform init
terraform apply
```

No manual step needed for the job-runner identity — `databricks.yml`'s
`job_run_as_application_id` variable resolves the service principal's
`application_id` itself, by `display_name`, via a bundle variable `lookup` (one of
the few places Terraform's state and the DAB bundle's deploy-time resolution line up
without a manual copy).

```bash
cd ..
databricks bundle deploy -t prod
```

Run `src/utility/create_snowflake_catalog_integration.ipynb` **manually, once**, in the
workspace (widgets: `catalog_name`, `secret_scope` — the workspace host is
auto-detected via `spark.conf.get("spark.databricks.workspaceUrl")`, no need to pass
it) — it creates the Snowflake catalog integration the job's sync task depends on.
Skipping this means
`sync_to_snowflake.ipynb` will fail trying to create `ICEBERG TABLE`
objects against an integration that doesn't exist yet.

```bash
databricks bundle run f1_ingest_and_transform_workflow -t prod
```

One apply, no second pass: the service principal's grant (`databricks_access.tf`) is
on the **catalog**, not the `analytics` schema, so it doesn't need the DAB bundle to
have created anything first — Unity Catalog privileges granted at the catalog level
cascade to every schema/table inside it, present and future. (An earlier version of
this granted schema-by-schema and needed a `gold_schema_exists`-gated second apply; the
catalog-level grant made that unnecessary.)

Delete/secure `terraform.tfvars` once applied — treat it the same as any other file
holding raw private keys.
